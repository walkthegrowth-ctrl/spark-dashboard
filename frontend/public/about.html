Spark Dashboard

Lightweight hardware monitoring for the NVIDIA DGX Spark (GB10).

Follow @walkthegrowth for information and updates

What this is

Spark Dashboard is a lightweight, self-hosted monitoring panel for the NVIDIA DGX Spark (GB10) and similar hardware. It’s an early-stage release (MVP) that complements the official NVIDIA DGX Dashboard rather than replacing it: thermal visibility and history, MemAvailable-aware memory reporting, per-core CPU and GPU load, and GPU power draw — in a clean, low-noise layout.

Data is collected on the Spark by a spark-collect daemon that samples hardware metrics and persists them to a local SQLite database. A separate spark-serve process exposes a small REST API and serves this frontend as static assets. The browser polls the API (REST + polling, not WebSocket streaming) and renders the charts client-side, so the Spark side stays quiet when no one is looking.

The install is small and self-contained — two Rust binaries and a static web page beside them, with sensible defaults: run spark.sh start, open the browser, and the machine tells you what its thermals, memory, and compute look like, with a short history you can scroll back through.

Notes and known limitations

Spark Dashboard is a monitoring tool for the author’s own machine that is being iterated on in the open. It is early-stage, and some parts are best understood as “bright but narrow” rather than “complete”. What this project does not do yet, and what it does only approximately, is listed here deliberately so readers can calibrate before acting on the numbers.

  • Read-only and local — the dashboard reports what the machine is doing; it does not drive it. Power/reboot stays with the NVIDIA dashboard. Not yet implemented: LLM engine detection, Tailscale status, and remote access (the server binds to 127.0.0.1 by default and has no authentication).
  • Time-box values are small-sample averages — the 5m, 15m, 60m (and GPU 1m/5m/15m/60m) cells are not the load observed over that full window. They are computed as a simple average of whatever samples the database happens to contain in the last 5/15/60 minutes (CPU: the load_1 average, normalised by core count; GPU: utilization.gpu samples). Right after install, that can be a handful of samples spanning a few seconds — so a 60-minute box can show a value that is really a 10-second average. Once the collector has been running long enough that the DB spans the full window, the values are honest.
  • Thermal zone names are approximate — the Linux kernel exposes temperature zones via /sys/class/thermal/thermal_zone* without a stable “part identifier”. The dashboard labels acpitz zones (SoC/package sensors: TMP461/TMP451 remote + Tj) heuristically by matching them against GPU temperature and then freezes that mapping for the collector’s lifetime. Under heavy GPU load the hottest core zone can move around, so a specific zone label may swap identity on a reboot, and a zone labelled “Composite” is not a guarantee of which silicon it actually covers.
  • Power is partial — the “Power” figure is what nvidia-smi power.draw reports (the GB10 unified package on the GB10 reference board). It is not a wall outlet measurement, does not include the ARM CPU and peripheral rail breakdown, and will show — when the GPU is not responding or the driver is in a transition state. The 120 W ceiling in the bar and chart reflects the power.draw reading, not a hardware cap.
  • GPU load is a single number — only the aggregate utilization.gpu from nvidia-smi is exposed today; the per-SM utilisation that is the interesting signal for LLM workloads is not sampled. The “GPU SMs” radar simply replicates the global utilisation across 48 spokes to give a visual surface, not 48 independent measurements.
  • History is capped on purpose — rows are stored for retention_days (default 7) and trimmed at most once every 6 h. On a heavily-loaded box this can be tens of megabytes; on an idle box it is a few megabytes. The in-memory charts in the UI are limited to the last ~1 h of samples (3600 at the default 5 s interval).
  • Local-first assumption — sampling runs only while both processes are up. No sampling happens offline or on battery backup. On a DGX Spark with the LLM running, CPU utilisation will often read near zero (all the work is happening on the GPU), so watch both cards, not just CPU.

Creator & technologies

This dashboard is built by Embracing Challenges (@walkthegrowth), a hands-on local-AI tinkerer. It’s closer to the monitor I wanted on my own desk: clearer thermal and power visibility, with memory and compute stats, and including a link back to NVIDIA’s dashboard to access the official tools.

If you run a Spark or a GB10 OEM box and care about owning the stack instead of renting it, follow the work and the next releases on X at @walkthegrowth.

The software is intentionally small — two Rust binaries, one Svelte frontend, and a SQLite database. It was developed with OpenCode (an open-source AI coding agent) running Qwen3.8:27b, with the design and process led by the author:

  • Backend — Rust (Rust 2021). spark-collect samples hardware (meminfo, thermal zones, CPU, GPU, power) on a timer; spark-serve is a tiny HTTP server (tiny_http) that reads the SQLite DB and answers requests.
  • Storage — SQLite (WAL mode) for history; the collector writes, the server reads, and both can run concurrently without locks.
  • Frontend — Svelte 4 + Vite. The chart library is a single file Sparkline.svelte — no external chart deps.
  • Distribution — Rust backend and Svelte frontend are built separately (cargo, Vite) and shipped as one self-contained bundle, installed with a single curl | sh line and managed with spark.sh.
  • Hardware — NVIDIA DGX Spark (GB10), aarch64, unified coherent memory. All sensors are read through the standard Linux /proc and /sys interfaces plus nvidia-smi.
